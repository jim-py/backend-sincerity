# Локальная Ollama: серверный API

> Основной запуск AI теперь через Docker: [DOCKER_AI.md](DOCKER_AI.md). compose.override.yaml добавляет API/worker/миграцию/Unix relay к текущему Compose. Ниже сохранены API-контракт и альтернативный host-side запуск; утверждения «Dockerfile/Compose не менялись» относятся к первоначальному этапу, не текущей контейнеризации.

Изменён только этот backend. Сервис историй `/stories` на прежнем порту, Android и frontend не изменяются. AI запускается отдельными контейнерами: опубликованный HTTP на **127.0.0.1:3012** и worker без HTTP-порта. Используется **та же PostgreSQL**, новая БД не создаётся. Новых npm-зависимостей нет. Host-side запуск остаётся доступен без OLLAMA_SOCKET_PATH; в нём bind по умолчанию 127.0.0.1. В Docker AI_BIND_HOST=0.0.0.0 внутри контейнера, а доступ с хоста ограничен loopback-публикацией.

## Принятый временный контракт

По уточнению владельца пользовательской авторизации пока нет. **Все четыре AI-маршрута защищены одним отдельным `Authorization: Bearer <AI_SERVICE_KEY>`**. Он не совпадает с ADMIN_TOKEN и не предоставляет DELETE `/stories`. Значение генерируется `npm run ai:key` в исключённый из Git `.env` и не печатается. Повторная команда сохраняет уже заданный ключ.

Это серверная интеграция: Productivum должен обращаться со своего backend. Не передавайте ключ в React, Android, публичные env, URL или bundle. Запросы с Origin отклоняются; CORS не включён. Произвольный X-Forwarded-For не используется. Все обладатели ключа имеют доступ ко всем AI-источникам и статусам задач: **`source` — имя снимка, не пользователь и не граница доступа**. Аккаунтов, JWT и фиктивной проверки владельца нет.

Источник привычек и его схема ещё не определены. Сейчас POST принимает **любой JSON**: объект, массив, строку, число, boolean или null. Для одного `source` хранится последний снимок; новый POST заменяет предыдущий, но предыдущий успешный отчёт остаётся до готовности нового. Это не история всех присланных событий.

**Текущий отчёт — обзор структуры JSON, а не статистика привычек.** Backend определяет тип значения и число полей/элементов верхнего уровня. Исходные имена, строки, клиентские проценты и другие значения в модель не передаются. Ollama выбирает заголовок и рекомендацию из проверенных вариантов JSON Schema; числовая строка сводки формируется backend и должна точно совпасть с enum схемы. Поэтому модель не может приписать число другой метрике, вставить HTML, инструкции или выдуманную статистику. Это намеренное ограничение до согласования схемы Productivum. Проценты выполнения, серии, расписания, архивирование и пользовательская история здесь **не реализованы**, поскольку входных правил и данных ещё нет.

## Маршруты

Общий размер тела — **32 KiB в байтах** после HTTP-декодирования; сжатие не принимается. Только UTF-8 `application/json`, глубина JSON не более 12, без NUL, непарных суррогатов и бесконечных чисел. Неизвестные query-параметры и повторяющиеся параметры отклоняются. Все ответы `Cache-Control: no-store`.

### POST `/ai/habit-summary?source=productivum&timezone=Europe/Moscow&language=ru`

Тело — сам произвольный JSON, без обязательной обёртки. `source`: ASCII-буквы, цифры, `_`, `-`, 1–80 символов, по умолчанию `default`. `timezone`: IANA, по умолчанию AI_TIMEZONE, затем UTC. `language`: ru/en, по умолчанию ru. Каждый POST задаёт метаданные заново; для постоянной зоны/языка передавайте их каждый раз.

- 200: тот же снимок и актуальный готовый отчёт; повторной генерации нет.
- 202: новая или уже существующая queued/running задача. Например:

```json
{"report":null,"period":{"start":"2026-11-02","end":"2026-11-08"},"timezone":"Europe/Moscow","current":false,"jobId":"UUID","state":"queued","statusUrl":"/ai/jobs/UUID"}
```

Параллельные одинаковые запросы получают одну задачу. При перегрузке 429/503 снимок не заменяется: транзакция откатывается, запрос можно повторить позже.

### GET `/ai/habit-summary?source=productivum`

200 с `report`, `current`, `state`, `job`; для существующего источника также `period` и `timezone`. До первого POST: `{"report":null,"current":false,"state":"empty","job":null}`. Готовый `report` содержит ровно `title`, `summary`, `advice`, `generatedAt`; дата формируется backend в UTC. Во время обновления возвращается предыдущий отчёт с `current:false`. GET не меняет снимок и не ставит задачу; модель не вызывается. Технический rate limiter пишет только счётчик запросов.

### GET `/ai/jobs/:jobId`

200: jobId, state (queued/running/succeeded/failed), безопасный error, createdAt, completedAt. Для завершённой сводки — published: было ли разрешено опубликовать результат. payload, промпт, исходный JSON и ответ chat не возвращаются. Нет задачи или она уже удалена по сроку хранения — 404. Доступ по общему сервисному ключу, без выдуманных владельцев/администраторов.

### POST `/ai/v1/chat/completions`

Поддерживаемое подмножество Chat Completions:

```json
{"model":"qwen3.5:35b-a3b-q4_K_M","stream":false,"max_tokens":200,"messages":[{"role":"user","content":"Коротко объясни пользу расписания."}]}
```

Разрешены только `messages`, необязательные `model`, `stream:false`, `max_tokens`. Модель фиксирована. От 1 до 8 текстовых сообщений; роли system (только первым), user, assistant; нужен user и последнее сообщение user. Внутри сообщения только role/content. Суммарно **2048 UTF-8 байт текста**, непустые строки. `max_tokens`: целое от 1 до AI_MAX_TOKENS, серверный максимум 350. Это консервативный входной предел с резервом под шаблон и выход, **не точный подсчёт токенов**. Доступные фактические prompt_eval_count/eval_count дополнительно сверяются с контекстом/выходом.

Tools, images, options, URL, temperature, загрузка/выгрузка модели и любые неизвестные поля клиента запрещены. Никаких внешних AI-fallback. Ответ синхронный 200 с id, object=`chat.completion`, created, model, choices; finish_reason stop либо length. usage присутствует только при фактических корректных счётчиках Ollama. Поток и полная совместимость OpenAI API не заявляются. Chat-текст может быть произвольным: потребитель должен отображать его как текст, не выполнять HTML.

### Ошибки

Единый JSON `{"error":"код"}` без исходных исключений. 400 — JSON/параметры/модель/контекст; 401 — нет/неверный ключ; 403 — Origin; 404 — путь/задача; 405 с Allow — метод; 413 — размер; 415 — Content-Type/encoding; 429 — rate_limited/queue_full с Retry-After; 502 — ошибка/невалидный ответ модели; 503 — БД, очередь или generation_blocked; 504 — тайм-аут. Непредвиденная внутренняя ошибка — 500. У сводок ошибки генерации видны в задаче; старый успешный отчёт сохраняется.

## Очередь, ночное расписание, кэш

Миграция `sql/002-ai.sql` транзакционно добавляет только schema ai: sources, jobs, reports, control, rate_limits. public.stories и её данные не меняются. Миграция повторяема и применяется явно; старый Docker volume автоматически её не получит. Служебная БД/Redis не нужны.

Все экземпляры должны использовать одну БД. Admission-секция сериализована PostgreSQL advisory xact lock; есть предел очереди и общий/поключевой rate limiter. SELECT FOR UPDATE + SKIP LOCKED и session advisory lock удерживают один слот на всё время inspect/load/generation, включая несколько worker. Уникальный partial index дополнительно защищает дедупликацию активных сводок.

Worker подогревает модель пустым messages при первой задаче, затем использует keep_alive=30m и прогретую модель для следующих задач. Сам Ollama не запускается и не выгружается этим приложением. Существующие сторонние потребители Ollama не подчиняются нашим PostgreSQL-lock: ограничение одного вызова гарантируется **внутри этой интеграции**, не для произвольных приложений на сервере.

Очередь имеет отдельный срок ожидания; загрузка и генерация имеют отдельные тайм-ауты. Подтверждённые временные отказы повторяются с ограничением попыток и backoff. Отмена HTTP-клиента отменяет только его queued chat; уже running вызов дожидается завершения, не освобождая слот раньше. Ответ без done=true, транспортный обрыв, тайм-аут/неподтверждённая отмена оставляют **постоянный блокирующий флаг**. После падения worker новый worker видит прежний active_job и также блокирует генерацию: один только отпущенный advisory lock не считается доказательством остановки модели. Exactly-once внешняя генерация не обещается.

Планировщик встроен в worker, проверяет расписание примерно раз в минуту между задачами. Отдельный PostgreSQL session lock оставляет один логический scheduler. Источники выбираются порциями по 100. В 03:00 локального дня (или при первом проходе после этого времени) задача ставится один раз на сохранённый источник. Повторный локальный час при DST не дублирует дату; если час пропущен, обработка идёт в первый доступный момент после 03:00. Во время длительной генерации или простоя запуск задерживается; это не обещание точности cron до минуты. Пропущенные старые дни не догоняются массово: обрабатывается текущий локальный день.

Период кэша — последние 7 завершённых локальных календарных дней, текущий день исключён. **Это окно актуальности отчёта, а не фильтрация событий неизвестной схемы JSON.** Ключ включает source, канонический JSON, timezone, язык, период, модель, версии промпта и схемы. Изменение снимка/периода делает отчёт устаревшим. Публикация сравнивает ключ с последним снимком повторно в транзакции; старая задача не перезапишет новую. Снимки и последний отчёт хранятся до замены. Payload завершённой задачи очищается; chat-result удаляется после получения HTTP-обработчиком, при аварии — при следующей очистке после 5 минут. Завершённые задачи удаляются спустя сутки при очередном проходе worker. При выключенном/заблокированном worker очистка может задержаться. Резервные копии PostgreSQL подчиняются политике владельца сервера.

## Конфигурация

В `.env.example` перечислены все параметры. Для AI нужны `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` существующей БД и отдельный AI_SERVICE_KEY. Node `--env-file` не подставляет `${...}`: значения должны быть заданы явно. ADMIN_TOKEN нужен прежнему stories API; AI его не использует для доступа. Ollama URL намеренно фиксирован: http://127.0.0.1:11434.

| Параметр | По умолчанию |
| --- | --- |
| AI_PORT | 3012, только loopback; 3010/3011/11434 запрещены |
| AI_TIMEZONE | UTC |
| AI_QUEUE_LIMIT | 8 queued/running задач |
| AI_QUEUE_WAIT_MS | 120000 |
| AI_LOAD_TIMEOUT_MS | 600000 |
| AI_GENERATION_TIMEOUT_MS | 300000 |
| AI_MAX_TOKENS | 350, выше 350 запрещено |
| AI_REQUESTS_PER_MINUTE | 6 на ключ; общий лимит вдвое больше |
| AI_MAX_ATTEMPTS | 2, максимум 3 |

Ollama получает temperature=0.2, num_ctx=4096, num_predict из серверного лимита, stream=false, think=false, keep_alive=30m; сводки дополнительно format=JSON Schema. Параметры сверены с [официальным chat API](https://docs.ollama.com/api/chat), [структурированными ответами](https://docs.ollama.com/capabilities/structured-outputs) и [официальным примером preload](https://github.com/ollama/ollama/blob/main/docs/api.md). Тег есть в [каталоге Qwen3.5](https://ollama.com/library/qwen3.5/tags). Установленная на Ubuntu версия неизвестна: `ai:inspect` проверяет /api/version и /api/show без генерации; worker затем проверяет фактический preload с think=false. Это не заменяет smoke test конкретной версии. Скорость и размещение модели в VRAM не измерялись; драйверы/модели не устанавливались и не менялись.

## Запуск и ручные запросы

Развёртывание, проверка портов, Nginx, systemd и откат: [deploy/README.md](deploy/README.md). Файлы подготовлены, **на Ubuntu не применены**.

В существующей среде Node LTS и с доступом к текущей БД:

```bash
npm ci --omit=dev --ignore-scripts --no-audit --no-fund
npm run ai:key
# Дополните .env PG_* существующей БД и AI_*; не переписывайте текущие секреты.
node --env-file=.env src/ai/cli.js migrate
node --env-file=.env src/ai/cli.js inspect-ollama
# В двух отдельных терминалах, либо через подготовленные systemd units:
node --env-file=.env src/ai/server.js
node --env-file=.env src/ai/worker-main.js
```

Прежний `npm start`/Compose продолжает запускать stories; AI не включается неожиданно. Dockerfile/compose.yaml не менялись. В контейнере 127.0.0.1 относится к самому контейнеру: подготовленные AI systemd units предназначены для запуска **на Ubuntu-хосте рядом с Ollama**. PGHOST должен быть реально доступен этому процессу через существующий приватный маршрут к БД. Не указывайте `postgres` вне Docker-сети и не открывайте 5432 наружу ради запуска; при отсутствии такого маршрута сначала согласуйте подключение к действующей БД.

Готовые запросы — [ai.requests.http](ai.requests.http). Curl ниже выполняется пользователем после запуска. В Bash введите ключ без записи его литерала в историю:

```bash
read -rsp 'AI_SERVICE_KEY: ' AI_SERVICE_KEY; printf '\n'
export AI_SERVICE_KEY
BASE=http://127.0.0.1:3012
# После фактического развёртывания маршрута замените BASE:
# BASE=https://api.productivumtesting.ru

curl -i "$BASE/ai/habit-summary?source=productivum" \
  -H "Authorization: Bearer $AI_SERVICE_KEY"
curl -i -X POST "$BASE/ai/habit-summary?source=productivum&timezone=Europe/Moscow&language=ru" \
  -H "Authorization: Bearer $AI_SERVICE_KEY" -H 'Content-Type: application/json' \
  --data-binary @requests/ai-source.json
# Подставьте только UUID из ответа POST:
JOB_ID=REPLACE_WITH_JOB_UUID
curl -i "$BASE/ai/jobs/$JOB_ID" -H "Authorization: Bearer $AI_SERVICE_KEY"
# Повторяйте с backoff 10,20,40,60 секунд, соблюдая Retry-After; затем GET сводки.
curl -i "$BASE/ai/habit-summary?source=productivum" -H "Authorization: Bearer $AI_SERVICE_KEY"
curl -i "$BASE/ai/v1/chat/completions" \
  -H "Authorization: Bearer $AI_SERVICE_KEY" -H 'Content-Type: application/json' \
  --data '{"stream":false,"messages":[{"role":"user","content":"Ответь одним коротким предложением."}]}'
unset AI_SERVICE_KEY
```

Не повторяйте POST chat автоматически при потере ответа: идемпотентность chat не заявляется. Примеры общедоступного адреса не означают, что маршрут уже развернут или проверен.

## Ручной запуск и восстановление

`node --env-file=.env src/ai/cli.js summary productivum` ставит/переиспользует задачу для **уже присланного** источника по тем же правилам дедупликации и кэша. Принудительного обхода кэша нет. `diagnose` показывает только агрегаты очереди и флаги gate, без имён, данных, промптов и ключей.

Если generation_blocked: остановите только процессы этой интеграции; подтвердите по состоянию/журналам Ollama, что прежний вызов завершился или отменён. `/api/ps` показывает загруженные модели, **не доказывает отсутствие активной генерации**. Не выгружайте/не перезапускайте общий Ollama без учёта других потребителей. Только после подтверждения отсутствия активного старого вызова:

```bash
node --env-file=.env src/ai/cli.js recover --confirmed-idle
```

CLI откажет, если advisory lock ещё удерживает worker. Команда отмечает прерванную задачу failed и открывает gate; автоматического опасного восстановления по истечению lease нет. Затем запустите worker и повторите необходимый POST сводки. Это компромисс в пользу отсутствия параллельного обращения при неподтверждённой отмене.

## Проверки

`npm run check` — синтаксис; `npm test` — Node test runner, моки Ollama/HTTP, без listening port и без реальной модели. Проверки PostgreSQL включаются **только явно**: AI_TEST_DATABASE_URL указывает отдельную пустую БД с именем `*_test`, AI_TEST_ALLOW_RESET=YES. Они создают и в finally удаляют только свою schema ai; при уже существующей ai-схеме откажут. Никогда не указывайте действующую БД. До этого нужен обычный `npm ci` для pg; Codex БД для тестов не устанавливает/не запускает.

Фактические результаты и невыполненные пункты: [AI_VALIDATION.md](AI_VALIDATION.md).
